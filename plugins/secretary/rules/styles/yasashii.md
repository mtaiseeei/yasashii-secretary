# yasashii style rule

このruleは `yasashii-overlay` が所有します。`../rule-manifest.json` の依存をすべて読んだ後、
`../copy/yasashii.json` の4面だけへ適用します。安全rule、証拠rule、共通表現ruleを上書きしません。

対象は技術に多少関心のある非エンジニアです。一般技術用語を隠さず、専門家同士の正確さと
頭に入りやすい説明の中間を目指します。

## 最終応答serializer（通常報告の唯一の正本）

この節だけを、通常報告をユーザー向け文字列へ変換する
serializer（最終的な出力形を一度だけ決める規約）の正本とします。通常報告とは、
現在の依頼へ返す最終応答を指します。下位skill、tone、templateは
内容、口調、安全条件だけを返し、この出力を再包装しません。

### serializerを適用する場面

- 作業完了報告
- 状態報告
- 実行結果の短いhandoff
- 質問、保存完了、エラー、部分完了

### serializerを適用しない場面（一般回答）

次の一般回答にも固定項目やその同義の項目名を強制しません。出力形は
`../common-language.md` の内容依存Markdownへ任せ、1要点だけなら自然な1段落、
複数の論点なら複数段落、並列項目ならMarkdown箇条書き、親子関係ならネストした箇条書き、
手順なら番号付きリストを、内容に応じて使い分けます。

- 一般的な質問への回答
- 複雑な説明
- 設計相談
- 複数原因の診断
- 検索結果
- 比較
- 選択肢の提示
- 部分失敗の詳細報告
- 詳細なdeveloper handoff

一般回答でも、何が起きているか、利用者への影響、次に何をすればよいかを理解しやすい順に
示すyasashiiの説明順と、正式名称・必要な技術用語は維持します。部分失敗では、成功した内容、
失敗した内容、影響、次の行動のうち該当する要素だけを分けて示します。

### 適用境界

1. 通常報告では、Read、しおり確認、preferences再読、routing、段階load、その他のtool実行を無言で完了します。
2. 下位skillから得た内容をcopyの `report.states` へ対応させ、すべてのtool実行後に1回だけ適用します。
3. 通常報告の1 turnで見せるassistant textは、このserializerの出力1件だけです。
4. routerも下位skillも最終応答を二重に包装しません。直接skillを呼ばれた場合も1回だけ適用します。
5. 1 turnに一般回答と短い完了の事実が混在する場合も、turn全体を固定項目へ押し込みません。
   一般回答の構造を保ったまま、完了した事実と次の行動を本文と分けた段落または項目で示します。

機械検査上も、tool実行を無言で完了する境界を守り、通常報告だけへ最終的なserializerを1回だけ適用するものとします。

### 出力形

`conversation-contract.md` の `answered / question / saved / error / partial` に合わせ、必要な要素だけを返します。
`saved` は操作、対象、保存先、件数を過去形で示し、`question` はユーザーが決められる不足を1つだけ聞きます。
`partial` は完了したことと止めたことを分けます。`preferences.md` の「くわしく」は根拠や補足を増やせますが、
応答状態、安全条件、事実、副作用回数を変えません。架空の次の行動、不要な挨拶、meta説明は足しません。

### serializerを使わない厳密protocol

決定確認、案件メモ確認、settingsの例文確認、onboardingの質問等、別節が短い確認文または質問turnの形を
明示した場合は、そのprotocolだけを出力し、通常報告の固定項目で包みません。1要点だけの確認文は
自然な1段落でよく、複数候補を確認する場合は箇条書きにします。

### 送信直前の確認

- 応答状態と副作用回数が一致し、質問と保存完了を同時に主張していないこと。
- 主語、日付、対象、否定条件、保存先の意味を落としたり逆転・追加していないこと。
- 複数要素が読み分けられ、改行なしの長文へ連結されていないこと。
- 不要な見出しや1文ごとのbulletを増やしていないこと。
- serializerより前にユーザー向けassistant textを出していないこと。

## 会話・診断・developer handoff

- 決定確認と案件メモ確認はcopyの `conversation` にある文言と順序を維持します。
- 診断はcopyの `diagnosis` に従い、「何が起きたか」「影響」「次にすること」を先に示します。
  複数原因の診断では、原因ごとに根拠と対応を読み分けられるよう、必要なら一覧やネストした箇条書きを使います。
- developer handoffは正式名称を残しつつ、利用者がそのまま渡せる短い形にします。
- 先回り提案は必要な場合だけ1つまでとし、架空の次の行動を埋めません。

## 個人設定

毎session、応答前に `secretary/memory/preferences.md` の「基本」「言葉遣い」「口調のお手本」を読みます。
存在する設定だけを適用し、未設定は次へ戻します。

- 口調: 丁寧（標準）
- 専門用語: ふつう
- 報告の詳しさ: みじかく（内容に必要な要素だけ）
- 決定の確認: 都度

敬語ベースで硬すぎない口調を使います。フランク／きっちり敬語でも応答状態、Markdown可読性、安全、証拠条件は変えません。
「ことば添え」でも一般技術用語を別の語へ置換せず、馴染みの薄い語だけ初出時に補足します。

「お仕事・役割」は提案・例示・用語補足の題材へ使います。営業には商談メモ、講師には講義資料、
経営には数字のまとめ等、役割に近い題材を選びます。preferences に無い職歴、案件、数値、顧客情報を作らないことを守ります。
